# Серверные событийные обои и бытовые состояния

Спецификация серверной поддержки контракта 0.2 по пакету «Затонувшая чайная» 0.3. Контракт 0.1 продолжает поддерживаться. Генерация рисунков художником, сборка готового JPEG из слоёв и публикация результата — разные операции. Эта спецификация описывает последние две операции и автомат состояний. Приложения в область работ не входят.

## Сборка и публикация

Сборщик получает нормализованные входы, тему устройства и предыдущее успешно собранное состояние. Он рассчитывает рецепт, собирает JPEG и превью, создаёт JSON и кандидат состояния. Только успешное сохранение полного рабочего комплекта делает кандидат текущим состоянием автомата.

Публикатор получает уже готовый рабочий комплект. Он не получает новые погодные данные, не выбирает бытовой час, не пересчитывает рецепт, не вызывает Pillow и не изменяет автомат. Публикация может выполняться сразу после сборки существующим часовым запуском либо отдельно.

| Результат операции | Состояние автомата | Результат на сайте |
| --- | --- | --- |
| Ошибка расчёта, отрисовки или сохранения рабочего комплекта | Прежнее | Прежний |
| Сборка успешна, публикация ещё не запускалась | Новое собранное | Прежний |
| Сборка успешна, публикация завершилась ошибкой | Новое собранное | Прежний; готовый комплект можно опубликовать повторно |
| Публикация успешна | Не изменяется публикатором | Готовый комплект |

Это уточнение заменяет привязку состояния к успешной публикации из раздела 8 исходного `LIFE_CLOCK.md`. Схемы `build.schema.json`, `life-state.schema.json`, состав ключей и таблица переходов сохраняются. `previous_state` означает последнее успешно собранное состояние. Понятие «опубликованное состояние» в комментариях исходного эталона заменяется на «собранное».

## Размещение темы

Корень — существующий `views.root`; при его отсутствии `<artwork_calendar.markdown_root>/views`.

| Путь | Содержимое |
| --- | --- |
| `collections/<theme_id>/collection.json` | `schema: 1`, `type: "dynamic"`, `id`, `title` |
| `collections/<theme_id>/devices/<device_id>/theme.json` | Описание ровно одного устройства по схеме 0.1 или 0.2 |
| `collections/<theme_id>/devices/<device_id>/backgrounds/` | Исходные фоны устройства |
| `collections/<theme_id>/devices/<device_id>/layers/` | Полноразмерные PNG RGBA устройства |

ID совпадают с именами папок. В одной коллекции устройства используют одну версию формата JSON. У каждого устройства собственные правила, рисунки и точные размеры. Масштабирование и заимствование рисунков другого устройства при сборке запрещены. Архив темы формируется отдельно для каждого устройства. Отдельной системы версий рисунков нет.

Схемы 0.1 находятся в `games/dynamic_wallpapers_contract/`, схемы 0.2 — в `games/dynamic_wallpapers_contract/v0.2/`. Производственные рисунки «Затонувшей чайной» в присланном пакете отсутствуют; его JSON не является готовой к публикации темой без этих файлов.

## Входы

Используются все доступные к моменту `inputs.at` подтверждённые входы. Сутки не замораживают игровые слои. Реальный погодный источник обозначается «Погода Столицы Империи»; его технический пояс — `Europe/Moscow`. Адаптер явно передаёт пояс и контекст источника.

Контракт 0.2 содержит прежние 37 числовых полей и `derived.life_slot`: целое 0–23 либо null. Сервер рассчитывает слот сам, переданное входное значение не управляет решением. Разрешены `=`, `!=`, `<`, `<=`, `>`, `>=`; порог слота должен быть математически целым, но не обязан лежать в 0–23. Например, `< 24` допустимо.

Отсутствующий или null числовой вход не соответствует ни одному сравнению, включая `!=`. Неверные данные поставщика нормализуются к null. Некорректный уже нормализованный вход — ошибка расчёта. Поля, которые не меняют базовый рецепт, не блокируют бытовое действие.

## Две фазы правил

`phase` принимает `base` или `life`; по умолчанию `base`. Любая ссылка базового правила на `derived.life_slot`, в том числе в неисполняемой ветке вложенного условия, — ошибка темы. В контракте 0.1 новые поля не разрешены.

Сначала заново разрешаются все правила base. Выбранные базовые ID и порядки должны быть уникальны до вычисления ключа. Затем определяется слот. При null фаза life целиком пропускается, даже если её `when` равно true.

Выбранный бытовой слой с уже существующим ID целиком заменяет базовый слой. Новый ID добавляет слой. Прозрачность по умолчанию равна 1 и не наследуется при замене. Повтор ID внутри бытовой фазы — ошибка; порядок проверяется после объединения. Итог сортируется по `order`. Нельзя исправлять ошибочную базу последующей бытовой заменой.

`opacity: 0` делает выбранный слой невидимым, но его ID и порядок остаются заняты, а ссылка на исходник должна быть корректной. Переноса слоёв из прошлого кадра нет. Бытовая поза заменяет слой персонажа, а не рисует второй экземпляр поверх первого.

## Базовый ключ

`base_key` — SHA-256 канонического JSON: `version: "base-key-v1"`, `renderer_version`, точные размеры и отсортированные базовые слои. Слой содержит `id`, `asset`, `file`, SHA-256 рисунка, `order`, `opacity`. Прозрачность нормализуется: 1 и 1.0, а также 0 и -0.0 дают одинаковый ключ.

В ключ не входят бытовые замены, `at`, время получения данных, неиспользованные входы и настройки JPEG. Версия композиции относится к наложению слоёв; параметры JPEG учитываются отдельно в ключе готового изображения. Контрольные суммы исходников определяются при подготовке темы; каждый час весь комплект PNG не декодируется.

## Автомат

Область состояния: контекст источника и его ревизии, тема, устройство, размеры, IANA-пояс и версия композиции. Разные области не заимствуют состояние друг друга. Временные отметки содержат известное UTC-смещение; `-00:00`, отсутствие смещения и неизвестный пояс — ошибки. Пояс операционной системы не используется.

`L` — `inputs.at` в явном поясе. `H` — начало этого местного часа, записанное полным моментом UTC с датой. Проверки выполняются сверху вниз:

| Условие | life_slot | blocked_hour_start | reason |
| --- | --- | --- | --- |
| Нет предыдущего базового ключа | null | H | first_build |
| Базовый ключ отличается от предыдущего | null | H | base_changed |
| Предыдущий заблокированный час равен H | null | H | hour_blocked |
| Иначе | L.hour | null | stable_base |

Сравниваются базовые рецепты, а не итоговые кадры. Смена бытовой позы не блокирует автомат. Изменение в середине часа блокирует его остаток; возвращение базы к прежнему варианту в этом часу не снимает блокировку. Пропущенные часы не накапливаются.

## Запись сборки и управляющее состояние

Нормативная запись `build` содержит `schema_version: "0.2"`, `inputs`, `recipe`, `life`. `life` включает пояс, H, предыдущую пару ключ/блокировка или null, текущий ключ, блокировку, причину, контекст источника, версию композиции и `request_key`.

Управляющий `life-state` содержит `context_key`, `last_at`, `base_key`, `blocked_hour_start`, `request_key` и исходную запись `record`. Поля управляющего состояния должны совпадать с записью, к которой они относятся. Повреждённое состояние не подменяется догадкой о прошлом.

`request_key` учитывает исходные входы без вычисляемого слота, профиль темы, каталог SHA-256, контекст, пояс и версию композиции. Точный повтор последнего успешного запроса возвращает прежнюю запись с прежней причиной. Запрос с более ранним at не переписывает текущую сборку. Изменение правил или исходников не считается повтором только из-за того же at.

Серверный JSON текущего кадра сохраняет оболочку `dynamic-state` и данные JPEG, а для 0.2 дополнительно содержит `schema_version` и `life`. Вложенные inputs/recipe/life совпадают с нормативной build-записью. Рецепт и данные достаточны для серверного повторного расчёта без погоды, текущих часов и управляющего состояния.

## Хранение рабочего результата

Рабочие комплекты находятся вне сайта, под `<views.weather.state_dir>/dynamic/builds/`; если `state_dir` не задан, используется существующий погодный каталог состояния. Кандидат содержит текущий JPEG, превью, JSON, machine.json и дневные JSON истории. После полной записи один атомарный указатель выбирает этот комплект. До переключения прежний комплект остаётся текущим.

После успешной сборки промежуточные и прежние JPEG удаляются. Для неактивных контекстов сохраняются управляющее состояние и JSON истории, без прежних растров. На сайте также хранится один текущий кадр устройства с превью. История JPEG не создаётся.

Дневная история относится к успешным сборкам, включая моменты, которые пока не удалось опубликовать. Устройство может экспортировать архив JSON всех сохранённых контекстов. Архив темы содержит исходники выбранного устройства, архив состояний — JSON. Изображение пропущенного момента можно восстановить из темы и записи.

## Публикация

Публичные пути относительно `<output.root>/assets/arcade/views/` сохраняются: `dynamic/<theme_id>/devices/<device_id>/current.jpg`, `current-preview.jpg`, `current.json`, `states.zip`. Для 0.2 дневные JSON находятся в `states/<context_key>/<date>.json`. ZIP темы — `downloads/theme-<theme_id>-<device_id>.zip`.

Публикатор проверяет готовые байты по контрольным суммам и записывает только готовый комплект. При обычной ошибке записи прежние публичные файлы восстанавливаются. Повтор публикации не изменяет рабочий machine.json. Настроенный `publish_root` является отдельным назначением доставки и тоже не управляет автоматом.

## Прогноз и повторы

Прогноз рассчитывается последовательно на копии состояния: будущий час использует виртуальное состояние предыдущего будущего часа. Копия не меняет текущую сборку, её блокировку, историю и файлы. Прогноз не отрисовывает 24 будущих JPEG.

Серверный повтор получает архив темы устройства и сохранённый JSON. Он проверяет решение, рецепт, исходники и собирает JPEG. Для побайтного совпадения нужны указанные в записи Pillow/JPEG библиотеки. Получение новых погодных данных и продвижение автомата при повторе не выполняются.

## Проверка реализации

Обязательны проверки всех четырёх решений, A→B→A в одном часу, пропущенных часов, повторов времени при смене смещения, точного повторного запроса, старого at, разделения контекстов, базовых и итоговых конфликтов, замены целого слоя и null-фазы.

Отдельно проверяются: отказ отрисовки и записи рабочего комплекта; успешная сборка при отказе доставки; повтор публикации без погоды/Pillow/автомата; прогноз без изменения текущего состояния; повтор JPEG по сохранённой записи; совместимость прежних коллекций. Проверки матриц без рисунков не заменяют проверку размеров и визуального качества производственной темы.
